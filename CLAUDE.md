# HRV Bridge (working title, placeholder)

A deliberately minimal Android and iOS app that records a 1-minute morning
measurement from a Bluetooth chest strap and writes resting HR, rMSSD and SDNN
to the user's Intervals.icu wellness record. It is a bridge, not an analysis
tool: no charts, trends, baselines or readiness scores. Intervals.icu does that.

Owner: Paul. Repo: mularmularmular/HRVbridge, **public** (since 20 Oct 2026),
deliberately with **no licence**: do not add one. Public release planned
(Google Play first, App Store later), free, donation link outside the app.

## Sensors

- Standard Heart Rate Service 0x180D, Heart Rate Measurement 0x2A37 (notify).
- Flags byte: bit0 HR format (0=UINT8, 1=UINT16); bit1 contact detected;
  bit2 contact feature supported; bit3 Energy Expended present (+2 bytes);
  bit4 RR intervals present.
- RR values: UINT16 little-endian, unit 1/1024 s, oldest first. Convert with
  `rr_ms = raw * 1000.0 / 1024.0`, keep doubles, never round before maths.
- A notification may carry 0, 1, 2 or more RR values. Odd trailing byte =
  malformed, drop it.
- If bit2 set and bit1 clear: poor contact, tell user to moisten electrodes,
  do not start the clock.
- No device whitelist. Runtime detection: if no notification with bit4 within
  ~10 s, refuse HRV ("this sensor does not send beat-to-beat data").
  Plausibility: mean RR over 10 s should match 60000/HR within ~10%.
  Implemented robustly (decided 20 Oct 2026): mean of artefact-filtered RR vs
  60000 / median reported HR, so one ectopic beat or dropout in the window
  does not refuse the session.
- Intended sensors include Polar H10/H9/H7, Garmin HRM Dual/Pro, 4iiii Viiiiva,
  Suunto Smart Belt, Wahoo etc. Garmin RR over BLE is reportedly inconsistent:
  runtime detection handles it.

## Measurement protocol and maths

1. Connect (the strap row shows it). There is no separate check phase
   (decided by Paul 21 Oct 2026): it only acted as extra settling.
2. Stabilisation: 60 s default (configurable 0/30/60/90 s), data discarded.
   Its first 10 s also run the signal check (RR present, contact,
   plausibility); a failure aborts with the same messages. With 0 s
   settling the check runs on the first 10 s of the measurement. While
   contact is poor before the check has passed, that phase's clock waits.
   Implemented in the session state machine (`MeasurementSession` in
   `:core` and HRVCore); the maths are unchanged.
   Dial (decided by Paul 21 Oct 2026): the hand sweeps with the wall clock
   like a seconds hand (one turn over settling, one over the measurement,
   parked at 12 when done); accepted beats make the orange ring "breathe"
   (opacity about 35% to 100% over each RR interval) while measuring only.
   Both also run with Reduce Motion (Paul, 21 Oct 2026): the hand sweeps
   smoothly every frame, and the breathing is an opacity change only.
   The heart rate window is orange with white text.
3. Measurement: 60 s wall-clock, collect all RR.
4. Keep screen on (`FLAG_KEEP_SCREEN_ON`), foreground only. No background BLE.

Artefact handling (defaults, documented in-app):
- Range: drop RR < 300 ms or > 2000 ms.
- Relative: drop RR differing > 20% from median of previous 5 accepted RR.
- Until the first beat is accepted, the relative reference is the median of
  the first 5 in-range beats (so a first-beat artefact cannot become the
  reference). Implementation decision, not from literature.
- rMSSD uses only successive differences where both beats were accepted.
- Quality gate: > 5% removed or < 40 valid beats -> "Measurement unreliable,
  please repeat", no upload unless user overrides.

Formulas (NN = accepted RR in ms):
- RHR = round(60000 / mean(NN)) bpm (integer, Intervals stores int).
- rMSSD = sqrt(mean((NN[i+1] - NN[i])^2)) over valid pairs, 1 decimal.
- SDNN = sample SD (n-1) of NN, 1 decimal. Note: 60 s SDNN is a weak metric;
  literature supports 1-min rMSSD (Esco & Flatt 2014; Flatt & Esco 2016).

Store each session's raw RR array locally (JSON) for recomputation and support.
Provide a "share debug log" button (BLE events, parsed packets, results; never
tokens).
- Done: `filesDir/sessions/session-<UTC start>.json` (`SessionRecord`, raw RR
  unrounded, accept/reject per beat, config, result, `uploadedAt`). Share
  sends the in-memory log of the last session plus its JSON as plain text.
  Credentials are never logged, and `DebugLog` also redacts registered
  secrets (key, token, Basic header value) on export.

## Intervals.icu integration (verified 20 Oct 2026 against live OpenAPI spec)

Docs: https://intervals.icu/api-docs.html (spec served at /api/v1/docs),
OAuth: https://forum.intervals.icu/t/intervals-icu-oauth-support/2759,
Cookbook: https://forum.intervals.icu/t/intervals-icu-api-integration-cookbook/80090,
Terms: https://forum.intervals.icu/t/intervals-icu-api-terms-and-conditions/114087

Write:
- `PUT https://intervals.icu/api/v1/athlete/0/wellness/{yyyy-MM-dd}` (local date),
  JSON `{"restingHR": 52, "hrv": 68.4, "hrvSDNN": 61.2}`. Only supplied fields
  change, so retries are idempotent. `restingHR` int32, `hrv`/`hrvSDNN` float.
  `hrv` = rMSSD per the developer's forum statements (not stated in schema).
- `PUT /api/v1/athlete/0/wellness-bulk` with an array of records, each with
  `id` = date. Use it to flush the offline queue.
- Athlete id `0` = the token's athlete.

Auth (decided 20 Oct 2026 by Paul):
- v1 (Android and iOS): the user's personal Intervals.icu API key is the
  primary and only connect method. Basic auth, username `API_KEY`. The user
  pastes it on the connect screen (Intervals.icu > Settings > Developer
  Settings). Real uploads with the key in release builds too.
- OAuth is deferred. Keep the existing PKCE/OAuth helpers and their tests,
  but do not build the browser flow. Notes for later:
- OAuth 2.0 authorisation code + PKCE as a **public client** (no client
  secret in the app). PKCE/public clients announced 20 Oct 2026. When built,
  read the client ID from a Gradle property, never hardcode it.
  - Authorise: `https://intervals.icu/oauth/authorize?client_id=..&redirect_uri=..&scope=WELLNESS:WRITE&state=..&code_challenge=..&code_challenge_method=S256`
    (S256 only; verifier 43-128 chars of A-Z a-z 0-9 - . _ ~; challenge =
    base64url(sha256(verifier)) without padding).
  - Exchange within 2 minutes: POST form `client_id`, `code`, `code_verifier` to
    `https://intervals.icu/api/oauth/token`. Response: `access_token`, `scope`,
    `athlete {id, name}`.
  - Check returned `scope` contains `WELLNESS:WRITE` (users can deselect scopes).
  - Redirect URIs must be registered exactly; no wildcards. Custom scheme
    (e.g. `hrvbridge://oauth`) is used by other Android apps (Cadence uses
    `cadence://intervalsicu`), but not explicitly confirmed for public clients.
  - No refresh tokens (2021 statement). Treat 401/403 as "reconnect".
    Multiple tokens per athlete per app are allowed.
  - Disconnect: `DELETE https://intervals.icu/api/v1/disconnect-app` with bearer.
  - App is "Pending" until approved; OAuth flow does not work before approval.
- Rate limit ~10 req/s per IP. Irrelevant at 1 call/day.
- Store token encrypted: AES-GCM key in Android Keystore, ciphertext in
  SharedPreferences/DataStore. Exclude from auto-backup. Do NOT use
  androidx.security-crypto (deprecated).
  - Done: `CredentialStore` (prefs file `auth`, excluded in both backup
    rule files), Keystore alias `hrvbridge_credential`. Undecryptable data
    is cleared and treated as "not connected". The Keystore path itself is
    untested (Robolectric has no AndroidKeyStore); verify on a device.
  - The connect screen (shown first while not connected) stores an
    `ApiKey` credential. Without a credential, debug builds dry-run the
    upload; release builds report "not connected" and keep the session
    pending, so it uploads once a key is saved.
- No live Intervals.icu calls from cloud sessions. Tests use local servers.

Overwrite handling (decided): no locking. On the connect screen, tell users
that other services (Garmin, Oura, Whoop...) syncing resting HR/HRV to
Intervals.icu can overwrite these values, and that they should untick Resting
HR and HRV in those connections in Intervals.icu settings. Verify exact menu
labels before shipping. Optional lean check: next morning GET yesterday's
record, compare with what was uploaded, show a one-line hint if changed.

Draft connect-screen copy:
> **Keep your morning values intact**
> This app writes your resting HR and HRV (rMSSD, SDNN) to today's wellness
> record in Intervals.icu. If another service (e.g. Garmin, Oura, Whoop) also
> sends resting HR or HRV to Intervals.icu, it may overwrite these values.
> To prevent that, open Intervals.icu settings, and for each connected service
> untick Resting HR and HRV.

## Android specifics

- Manifest: `BLUETOOTH_SCAN` (`usesPermissionFlags="neverForLocation"`),
  `BLUETOOTH_CONNECT`, legacy `BLUETOOTH`/`BLUETOOTH_ADMIN` maxSdkVersion 30,
  `ACCESS_FINE_LOCATION` maxSdkVersion 30, `INTERNET`.
- Runtime: Nearby devices on 12+, location on 11 and lower.
- Scan filtered by service UUID 0x180D; remember last device; auto-connect.
  - Done (untested on a device): `BleHeartRateSource`. Scans with a 0x180D
    filter, connects at once if the remembered address shows up, otherwise
    after 3 s to the strongest strap seen; 20 s scan and 15 s connect
    timeouts. Enables 0x2A37 notifications via the CCCD, then calls
    `onConnected()`; the session (settling, with the signal check in its
    first 10 s) starts on Start. Packets are
    timestamped on arrival in the GATT callback. Every GATT callback goes
    to the debug log ("BLE" lines). Debug builds connect the simulated
    strap from Settings. UI per `docs/ui-implementation-brief.md`;
    `ScreenshotTest` renders every state into the `android-screenshots`
    CI artifact.
- Retry failed uploads on next app open (WorkManager only if really needed).
  Done: on app open (and right after saving a key) the newest submitted
  session per date is sent, if not yet uploaded, in one `PUT wellness-bulk`
  (`SessionStore.retryBatch()`), so an older submission never overwrites a
  newer one of the same day, and an unsubmitted newer session does not block
  an older submitted one. Nothing uploads automatically (Paul, 21 Oct
  2026): the result screen shows the values and "Upload to Intervals.icu"
  ("Upload anyway" if unreliable). Pending = result, never uploaded, and the
  user tapped one of those (stored as `uploadOverride`, same JSON key).

- Release signing (upload key): `app/build.gradle.kts` reads
  `HRVBRIDGE_KEYSTORE_PATH`, `HRVBRIDGE_KEYSTORE_PASSWORD`,
  `HRVBRIDGE_KEY_ALIAS`, `HRVBRIDGE_KEY_PASSWORD` from the environment, or
  `hrvbridge.keystore.path`, `hrvbridge.keystore.password`,
  `hrvbridge.key.alias`, `hrvbridge.key.password` from
  `~/.gradle/gradle.properties`. Without all four, release builds are
  unsigned (CI stays green). Never commit a keystore or passwords
  (`*.jks`/`*.keystore` are gitignored). Paul creates the upload key once,
  outside the repo, and keeps a backup:
  ```
  keytool -genkeypair -v -keystore ~/keys/hrvbridge-upload.jks \
    -alias upload -keyalg RSA -keysize 4096 -validity 10000
  ```
  then adds the four `hrvbridge.*` lines to `~/.gradle/gradle.properties`
  and runs `./gradlew :app:bundleRelease`. Use Play App Signing: Google
  holds the app signing key, this is only the upload key (resettable via
  Play support if lost).

  `test-vectors.json` (packaged as debug assets) as 1 Hz 0x2A37 packets via
  the `HeartRateSource` interface the BLE code will implement. Speeds 1x,
  10x, 60x. Release builds get a stub (`app/src/release`). Upload is a dry

  Robolectric tests in `app/src/testDebug` drive it end to end.
- Real recordings: `core/src/test/resources/recordings/<strap>-<yyyy-MM-dd>.json`,
  committed by Paul only (personal data). Format = HRVCore `RawRecording`
  as written by the iOS raw recorder: `{"version": 1, "startedAt": ISO 8601
  UTC, "deviceName", "deviceId", "packets": [{"tMs": ms since the recording
  started, "hex": raw 0x2A37 notification value}]}`. Expected values live in
  `<name>.expected.json` next to it, generated by
  `python3 -I tools/gen_test_vectors.py --recordings` (never edit by hand):
  whole-recording parse, filter and metrics, plus the measurement window
  the app would use (settling 30 s with the signal check in its first
  10 s, then 60 s: packets in [30 s, 90 s)). Tests:
  `RecordingTest` (Kotlin core) and `RecordingTests` (HRVCore).
- First recording (Polar H9, 21 Oct 2026, 2 min, 120 packets, 101 RR): the
  H9 does not report the contact feature (flags 0x10). Over the whole
  recording 16 beats are rejected while the heart rate settles in the
  first ~25 s (the known "HR shift > 20%" behaviour), so the whole
  recording is unreliable; the app's window ([30 s, 90 s) after 30 s
  settling) has 0 rejected, RHR 50, rMSSD 61.8, SDNN 58.3, reliable.
- Real-strap testing happens first on iOS (iPhone SE 2020). Record raw 0x2A37
  notification bytes from the H9 there and commit them as test vectors, so the
  Android pipeline is tested against real data too.

## Morning questions (optional, decided by Paul 21 Oct 2026)

- Off by default; Settings switch "Morning questions". When on, a result
  the user submits ("Upload to Intervals.icu" or "Upload anyway") waits on a questions
  page; "Upload" sends values and answers together, "Skip" sends values
  only. Answering without a measurement: skipped (not trivial).
- Every question is optional; unanswered ones are not sent (PUT only
  changes supplied fields). Native wellness fields, int 1 to 4, 1 = best,
  with Intervals.icu's own labels in this order:
  soreness 1 Low, 2 Avg, 3 High, 4 Extreme; fatigue 1 Low, 2 Avg, 3 High,
  4 Extreme; motivation 1 Extreme, 2 High, 3 Avg, 4 Low; injury 1 None,
  2 Niggle, 3 Poor, 4 Injured. Sent in the same wellness PUT and bulk retry.
- "Sick today?" No / Yes. Yes is a calendar event, not a wellness field:
  `POST /api/v1/athlete/0/events?upsertOnUid=true` with
  `{"category":"SICK","start_date_local":"<date>T00:00:00","name":"Sick","uid":"hrvbridge-sick-<date>"}`,
  sent after the wellness PUT; the per-date uid makes retries idempotent.
  No is not sent. A session stays pending until both are sent.
- Alcohol: skipped for now.
- Answers live in the session record (`answers`, explicit nulls), so
  retries include them. Tests use local servers only.
